Writing anchored Originals to Bitcoin (plan 011 PR 10; plan 012), in the new `@originals/sdk/originals/bitcoin` entry. `prepareEntryInscription` inscribes an Original's head entry on its anchoring sat through the sat inscription builder (the first funding UTXO must hold the sat, so only its holder can extend the Original, and the head must be the next entry Bitcoin can accept); `submitPreparedInscriptionOnSat` and `resumeInscriptionOnSat` give durable submission and same-pair retries; `readAnchored` reads the sat back, refusing a read of another network, so the published boundary is what Bitcoin shows, never pending intent. Committed entries Bitcoin does not show yet are caught up in order: `nextPendingEntry` compares the committed local head with the accepted Bitcoin head and lists the entries between them; `prepareEntryInscription` prepares the next of them by default, inscribing the stored signed line verbatim (an explicit `versionId` that is not next is `HEAD_NOT_NEXT`, and a caught-up Original is `NOTHING_TO_INSCRIBE`); and `catchUp` re-reads Bitcoin and the recorded pairs to return one step (`prepare`, `resume`, `wait-for-confirmation` or `done`), so a pending publication is resumed or waited on rather than prepared twice, an entry Bitcoin already accepted is never inscribed again, and each accepted entry lands in a later block. Verified end to end on Bitcoin Core 31.1 and ord 0.29.0 regtest. `catchUp` no longer needs `recoveryIds` when the recovery store can `list()` its records (the optional new `InscriptionRecoveryStore.list`); `fileRecoveryStore(dir)` in `@originals/sdk/originals/fs` is a durable one, one atomically written file per pair, and the regtest restart journey kills a writer between commit and reveal and resumes the identical pair from it in a fresh process (#975). Anchoring follows spec `a432aa67` (P9.17, P9.18): until Bitcoin shows the anchor, the inscription is the whole stored log from genesis through the anchoring entry (exact stored lines; `pair.carries`), then one entry per inscription; a body over 350,000 bytes is refused (`ANCHORING_LOG_TOO_LARGE`, also by `sdk.anchor` before committing; `INSCRIPTION_TOO_LARGE`). Before building a pair the writer verifies the stored log through the entry and every signer's identity evidence, author and editors (`ANCHORING_NOT_VERIFIED`, `ENTRY_NOT_VERIFIED`), and returns `offChain`: the resource bytes and did:vh/did:webvh signer DID histories Bitcoin will not hold. `readAnchored`, `nextPendingEntry` and `catchUp` label a broadcast anchor `publication: "pending-bitcoin-acceptance"` until Bitcoin shows it (pass `recoveryStore` to `readAnchored`). Every read names its index (`index`, now required). `transferHandoff` exports, for the recipient of the anchoring sat, the evidence the sender holds, and `verifyHandoff` checks it against the sat. Editor entries are inscribed like author entries. `OriginalsSDK.committedLog(did)` returns the stored log, unverified. Recovery is checked as strictly as preparation: `catchUp` verifies the log through the entry again before saying `resume` (P9.18) and otherwise returns `refused` (nothing sent; `commit` says how far the pair got and `ifRevealed` whether Bitcoin would ignore its reveal), and `resumeEntryInscription` resumes only the pair `catchUp` chose. A pair can still land only while the sat read shows the sat in its funding input or its own outputs, before the anchor is accepted as after; among several the one furthest along wins, then the lowest recovery id. `pending-bitcoin-acceptance` now requires the pair to be observed (confirmed, or in the node's mempool via the new optional `inMempool` on `getTransactionStatus`, reported by `RegtestProvider` and, for mempool entries, `QuickNodeProvider`); a pair submitted but not observed is `submitted-unobserved`. A broadcast pair the node reports in neither its mempool nor the chain is resumed as the same pair; indexes that disagree (`unverified`) give `wait-for-bitcoin`, never a second anchor. Each recovery record is validated (its declared txids must match its bytes) and a damaged one is skipped and listed in `recoveryIssues`, never blocking other Originals. `prepareEntryInscription` takes the recovery store and refuses `PAIR_IN_FLIGHT` while a pair for the same entry can still land, unless `replaces` names it (P9.6); `replaces` from `catchUp` lists only inscriptions Bitcoin ignored for good, not ones unconfirmed or disputed.
