## Initial read-only production observations, 2026-09-06

The Railway production `builder` service currently serves commit
`9116ce2c364872f7993336050786e722da86c2e2` on `originals.build`. The release candidate
has not been deployed. `/data` is mounted on the existing 50 GB volume;
`NODE_ENV=production`, `BTC_NETWORK=mainnet`, `VITE_BTC_NETWORK=mainnet`,
`VITE_WEBVH_HOST=originals.build`, and `TRUSTED_PROXY_HOPS=1` are configured.
Required auth variable names are present; this does not verify live OTP signing.

The initial check identified three unresolved prerequisites:

1. The configured QuickNode status has `sat_index=true`,
   `inscription_index=true`, and `address_index=false`. The released snapshot
   contract requires all three indexes and a stable common Core/ord tip. Supply
   a provider meeting that contract; do not turn an incomplete observation into
   an accepted identity.
2. Neither raw binary content transport nor an explicit base64 gateway contract
   is configured. Supply `QUICKNODE_CONTENT_BASE_URL` (HTTPS ord-compatible raw
   `/content/:id`) or a verified `QUICKNODE_CONTENT_ENCODING=base64` gateway.
   Verify a known PNG's exact SHA-256 through the actual production provider.
3. The production volume API returns no backup schedules and no backup snapshots.
   Enable the agreed backup schedule, record its retention, and verify a backup
   and a restore into an isolated destination before relying on hosted durability.

Receipts: [production properties](evidence/production-preflight.json) and
[provider capabilities](evidence/production-provider-capabilities.json). Secrets
and provider URL values are deliberately absent. These observations can drift;
repeat them immediately before an approved deployment.

## Authorized preflight results, 2026-09-06

- **Raw PNG transport verified and configured.** The existing endpoint's
  `/addon/679/content/:id` route returned the same 793 PNG bytes as the original
  transaction witness for inscription zero, including when requested with the
  SDK's `Accept: application/octet-stream` header. SHA-256 is recorded in the
  [transport receipt](evidence/production-content-transport.json).
  `QUICKNODE_CONTENT_BASE_URL` now points at that verified add-on base; its secret
  value is omitted from evidence. Configuration was saved without triggering a
  deployment. The gateway labels the raw response `application/json`; the SDK
  reads bytes, and the witness comparison verifies their actual content.
- **Daily backups and an isolated native restore verified.** Daily retention is
  518,400 seconds (six days). The named pre-release backup was restored into a
  separate volume. Before committing the staged restore, its production mount
  swap was removed and the restored volume was attached only to a temporary,
  private maintenance service without app credentials or public domains.
  The verifier read 361 files (291,643 bytes), parsed all 50 JSON files, and
  recorded a deterministic file-manifest digest. Production retained its original
  deployment and volume throughout. The temporary service and restored copy were
  deleted; the original backup and daily schedule remain. See the
  [backup/restore receipt](evidence/production-backup-restore.json).
- **Complete provider indexing remains blocked.** The live provider still
  reports `address_index=false`; content transport alone does not satisfy the
  complete snapshot contract. QuickNode dashboard sign-in is required to inspect
  its available indexing configuration. The [SDK preflight receipt](evidence/production-snapshot-preflight.json)
  records its refusal to accept incomplete evidence. No index-completeness guard
  was relaxed.
- **Release deployment and owner journey remain pending.** Production still
  serves `9116ce2c364872f7993336050786e722da86c2e2`. Live Turnkey OTP, owner funding,
  the mainnet signed-pair submission and fresh public-host verification have not
  happened. Deployment approval is recorded; those missing observations are not
  additional approval gates.

## Prepared change and verification order

1. Review the release PR, code review and API freeze. The feature PR exits
   prerelease mode but retains pending changesets. The existing Version Packages
   PR is the single npm publication approval: merging its stable version commit
   can publish SDK 3.0.0, CEL 1.0.0 and auth 3.0.0 to `latest`. Do not merge the
   earlier prerelease Version Packages proposal as the stable release.
2. Resolve the remaining provider indexing prerequisite and recheck the completed
   transport/backup evidence for drift. Run the read-only
   `apps/landing/scripts/check-quicknode-ordinals.ts` with a confirmed outpoint,
   `BTC_CHECK_PNG_SAT`, and `BTC_CHECK_PNG_SHA256`. Require complete fresh sat
   evidence, exact bytes and current active-chain ordering. Missing configuration
   or an incomplete provider response is a failed gate.
3. Preview `.railway/railway.ts` against production. The recorded preview has
   only build/start/restart property changes and no deletions. It preserves the
   current Railpack builder, domain, volume, other services and existing operator
   values. Recheck the plan before applying; the saved preview is not approval.
4. On approval, deploy the reviewed candidate with the canonical domain and
   mainnet flag baked into the SPA. Verify startup configuration, mounted storage,
   canonical redirect, client IP handling and a real Turnkey OTP session whose
   bound public key matches the browser key. Re-login must clear a stale bound key.
5. Perform the owner-funded PNG journey through the deployed browser: sign in,
   upload the owner's PNG (at most 32 KiB), create, publish, deposit confirmed BTC,
   inspect the actual full-envelope quote, and submit the persisted signed pair.
   Record quoted fee, maximum approved spend, funding txid, commit/reveal txids,
   inscription id, sat, did:cel, did:webvh and did:btco. A transport timeout is an
   ambiguous result; retry the same prepared pair from recovery.
6. Close the browser and verify the Original from a fresh browser with no local
   state. Require exact PNG bytes/digest, accepted CEL head, derived DID controller,
   separate possession observation and confirmation evidence. Verify the earlier
   WebVH identity still resolves and its PNG remains byte-identical. Record any
   UI defect before changing the candidate; changed code needs renewed evidence.
7. Verify background reconciliation and retained recovery through the configured
   six-confirmation horizon. Monitor named `inscribe_failed` persistence errors,
   stale recovery records and provider incompleteness. Storage errors must surface
   as failure, never as successful durable recovery.
