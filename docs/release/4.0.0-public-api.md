# SDK 4 / CEL 2 public API sign-off

This freeze covers the five `@originals/sdk` entry points signed off for
3.0.0 (root, `/v3`, `/cel`, `/types`, `/testing`) plus one new entry point
added since, `/asset-envelope`; the five carried-forward entry points' scope
decisions and symbol-by-symbol "keep" list otherwise carry forward unchanged
from [docs/release/3.0.0-public-api.md](3.0.0-public-api.md). This document
records only what changed since that freeze — the removed identity
compatibility knobs (#583/#628/#654), the previous-format CEL writer surface
moving behind `@originals/cel/legacy` (#597/#649), the credential
verification safe-default (#600/#613/#653), the hosting-evidence additions
(#601/#622), the new `/asset-envelope` entry point, the independent
chain-assurance and per-resource availability additions (#635/#652), the
pending-resolution status and independent enumeration/ownership/content
cross-checks that close out #594 (#662/#665/#669/#670/#671) — and
reproduces each of the six export tables in full so the inventory stays a
single authoritative list rather than a diff a reader has to apply by hand.
As with 3.0.0, every symbol marked **keep** below is supported within its
documented purpose and semantic-version contract; only the package exports
map and CLI are supported entry points; deep files included in `dist/`
remain implementation details.

## Changes since 3.0.0

### Renamed

| SDK 3 / CEL 1 | SDK 4 / CEL 2 | Notes |
| --- | --- | --- |

### Behavior change: credential verification is safe-by-default (#600)

`CredentialManager.verifyCredential` and the exported `Verifier.verifyCredential`
(`checkStatus` defaults to `true`) no longer verify on signature alone when a
credential declares `credentialStatus`. With a `statusListResolver`
configured, the declared status is actually evaluated (every entry, singleton
or array — #592/#613); without one, such a credential now **fails closed**
instead of silently passing. Callers that want the previous signature-only
behavior call the newly, explicitly named `verifyCredentialSignature`
(`CredentialManager`) or pass `{ checkStatus: false }` (`Verifier`) instead.
This is a breaking change for any caller relying on the old default: a
credential that previously verified only because its declared status was
silently unchecked no longer does.

`packages/sdk/src/verify/UnifiedVerifier.ts` prototypes a further
`assurance: { signature, status, freshness }` breakdown on top of the same
safe-by-default status check, but its own header marks it "SPIKE / PoC — NOT
a shipped API," and it is not exported from any of the six entry points
below. It is not part of this freeze; mentioned here only so a reader
searching the source for `assurance` doesn't mistake it for shipped surface.

### VC Status List: kept as supported interoperability

The freeze's Status List question (raised against #592/#613/#634) is
resolved by what actually shipped: `StatusListManager`, `BitstringStatusList`,
`StatusListResolver`, `Verifier`, and `CredentialManager` remain public root
exports. The array-form bypass is fixed (#613) and ordinary verification is
safe-by-default (#600, above), so the surface is kept as supported VC
interoperability rather than narrowed or deprecated. No further Status List
API changes are expected for this freeze.

### Previous-format CEL writer surface moved behind `@originals/cel/legacy` (#597)

`@originals/cel`'s root no longer exports `OriginalsCel`, the three
per-layer managers (`PeerCelManager`/`WebVHCelManager`/`BtcoCelManager`), the
event-log algorithms they delegate to (`createEventLog`, `appendEvent`,
`updateEventLog`, `deactivateEventLog`, `verifyEventLog`, `witnessEvent`, the
custody-fold helpers), the previous-format canonicalizer (`canonicalizeEvent`
and derivatives — this was also issue #599's RFC 8785 finding: the flawed
canonicalizer is no longer reachable from the package root at all, previous
format or not), or the previous-format signer helpers
(`celSignerFromKeyPair`, `createKeyStoreCelSigner`, `currentControllerVm`,
`hexSha256ToDigestMultibase`). All of it moved together to the new
`@originals/cel/legacy` subpath (`packages/cel/src/legacy.ts`). This surface
was never part of the `@originals/sdk` 3.0.0 freeze above (previous-format
support was always an internal-consumer detail of the CEL package, not an
SDK lifecycle fallback — see that document's "Decisions and scope"), so it
does not change any row in the tables below; it only closes the gap where a
new consumer could reassemble a previous-format writer from root "primitive"
exports without ever importing a manager by name.

### Added: hosting evidence and public reachability (#601)

`publishToWeb`/`HostedAssets.publish()` can now report explicit
`hostingEvidence: 'adapter-asserted' | 'independently-verified'` instead of
implying every successful adapter-local write is publicly reachable. A
caller opts in to independent verification with a `publicReachability`
checker (`PublicReachabilityCheck`) passed via `HostedAssetsOptions`;
`fetchPublicReachabilityCheck` is the default HTTPS-only, redirect-refusing,
size-and-time-bounded implementation. Both reachability options default off
(unchanged adapter-asserted behavior unless a caller opts in); wiring a
specific deployment to require independent reachability by default is a
deployment/operator decision, not an SDK API one, and is out of scope here.

### Added: canonical identity helpers, envelope inspection, history checkpoints

`deriveAssetId`, `normalizeAssetId`, `sameAssetIdentity`, `assetDigest`,
`assetIdFromDigest`, `AssetAlias`/`parseAssetAlias` (identity, #586/#654),
`parseAssetEnvelope`/`inspectAssetEnvelope`/`AssetEnvelopeInspection`
(envelope reading), and `HistoryCheckpoint`/`checkpointFromHistory` (freshness
checkpoints consumed by `UnifiedVerifier`) postdate the 3.0.0 freeze and are
now part of the supported surface below.

The envelope-reading trio above is also exposed through a new, sixth entry
point, `@originals/sdk/asset-envelope`, added so that offline envelope
validation can be imported without pulling in the hosting, Bitcoin, or
custody modules reachable from the package root. The subpath re-exports the
same `parseAssetEnvelope`, `inspectAssetEnvelope`, and
`AssetEnvelopeInspection` already listed under the root/`/v3`/`/types`
tables, plus the `AssetEnvelope` type itself; none of the four are new
symbols, only newly reachable through a narrower entry point. See its own
table below.

### Added: independent chain assurance and per-resource availability (#635, #652)

Both items the previous revision of this document deferred have since
landed on `main` and are part of this freeze.

`resolveSat`'s accepted `SatResolution` (and the SDK's `AssetResolution`/
`AssetDIDResolution`) now carries `chainEvidence: { assurance: 'provider-asserted'
| 'node-validated', source?: string }`. A snapshot's own `chainEvidence` claim
can never self-upgrade the result — `assurance` reads `'node-validated'` only
when the caller configured an explicit `chainValidator` (`OriginalsSDKOptions`)
and that validator's own check of the snapshot's tip, active block hashes, and
reveal-transaction membership against a separately trusted Bitcoin node
succeeded; a configured validator that throws or disagrees fails resolution
closed rather than silently reporting `provider-asserted`. `createBitcoinCoreChainValidator`
(new export, root/`/v3`) is the shipped implementation, and `ChainValidator`/
`BitcoinCoreChainValidatorOptions` are its supported types. This was a scoped
increment of #594, not its close-out at the time: Ordinals enumeration
completeness, sat ownership, and inscription content/metadata interpretation
were still provider-asserted dimensions tracked separately. The additions
below close out the remaining #594 scope, and #594 itself is now closed.

### Added: pending resolution status for unconfirmed sats (#662)

`SatResolution` (and the SDK's `AssetResolution`/`AssetDIDResolution`) gains
a third non-accepted variant, `status: "pending"`, distinct from
`"not-found"`. `"not-found"` still means either no publications were
observed for the sat at all, or confirmed data was inspected and no valid
boundary was found in it. `"pending"` means the complete observation
contains only unconfirmed publications for the sat — something was
broadcast, but nothing has reached the snapshot's confirmation depth yet, so
no boundary could be evaluated either way — and carries the observed
unconfirmed publication ids as `pending: readonly string[]`
(`didDocumentMetadata.pending` on `AssetDIDResolution`). This is a behavior
change for a caller that previously treated every non-`"accepted"` status as
equivalent terminal absence: an all-unconfirmed sat that used to resolve as
`"not-found"` now resolves as `"pending"`, and a caller distinguishing "never
published" from "published but not yet confirmed" must check for it
explicitly. `did.resolveDID()` is unaffected in kind — it already threw
`ASSET_RESOLUTION_INCOMPLETE` for any non-`"accepted"`/non-`"not-found"`
status before this change, and continues to do so for `"pending"`.

### Added: independent enumeration, ownership and content cross-checks (#665, #669, #670, #671)

Three new optional, independently-sourced corroboration dimensions round out
the #594 chain/index-assurance work, alongside a wording correction:

- **Enumeration** (#665): `resolveSat()` accepts `independentEnumeration: {
  source, inscriptionIds }` — every inscription id a second, independently
  configured Ordinals index currently reports for the queried sat. An id
  present there but absent from the primary snapshot fails resolution closed
  with `inconsistent-evidence` rather than accepting a possibly-omitted
  history. The accepted result's `enumerationAssurance` reads
  `"cross-checked"` only when such a source was consulted and agreed;
  otherwise `"provider-asserted"`. `enumerationSource` carries the source's
  non-secret label when cross-checked. At the SDK layer,
  `OriginalsSDKOptions.independentEnumeration: IndependentEnumerationSource`
  (new export, root/`/v3`) wires a second `SatProvider` for this check,
  failing closed if it is unreachable or reports an incomplete, unhealthy, or
  unstable snapshot.
- **Ownership** (#669): the same `independentEnumeration` source can also
  supply `ownership`, its own current sat-holder observation. `resolveSat()`
  fails closed if it disagrees with the primary snapshot's `owner`/`satpoint`.
  Satpoint comparison normalizes hexadecimal transaction-id casing in both
  observations; decimal output indexes and offsets remain unchanged. The
  exported `/cel` helper `normalizeSatpoint(string | null): string | null`
  applies this normalization, preserving null and malformed values (#751).
  The accepted result's `ownershipAssurance` reads `"cross-checked"` only
  when that independent ownership evidence was supplied and agreed;
  configuring `independentEnumeration` for enumeration alone does not itself
  upgrade ownership assurance.
- **Content** (#670): `resolveSat()` accepts `independentContent`, media
  type/content digests derived independently per confirmed inscription — for
  example by parsing a reveal transaction's witness envelope directly from a
  validating Bitcoin node rather than trusting the indexer's report. A
  disagreement fails resolution closed rather than accepting possibly
  substituted content. The accepted result's `contentAssurance` reads
  `"cross-checked"` only when independent content evidence was supplied and
  agreed for every accepted publication. `createBitcoinCoreContentValidator`
  (new export, root/`/v3`) is the shipped implementation, consumed via the
  new `OriginalsSDKOptions.contentValidator: ContentValidator` option;
  `ContentValidator`/`BitcoinCoreContentValidatorOptions` are its supported
  types.
- **Trajectory wording** (#671): the accepted result's `trajectoryAssurance`
  field is always `"not-independently-derived"` today — `ownership` remains a
  single point-in-time snapshot observation, never a walk of the sat's
  historical transfer graph from genesis, even when a second index source
  corroborates the same current holder. The field is reserved so a future
  independent-derivation capability has somewhere honest to report a
  stronger value.

All three cross-check dimensions default off (unchanged provider-asserted
behavior unless a caller opts in), surface identically through
`did.resolveDIDWithMetadata()`'s `didDocumentMetadata`, and are additive
fields/options — no previously listed symbol's shape narrows. With all three
landed, #594's full original scope (enumeration completeness, sat ownership,
and content/metadata interpretation, alongside the earlier chain-consistency
increment) is closed.

Alongside it, the accepted result also carries `resourceAvailability`: one
`{ id, version, availability: 'bitcoin-inline' | 'referenced' }` entry
(`ResourceAvailabilityRecord`, `ResourceAvailability`; both new exports —
note `@originals/sdk`'s own `ResourceAvailability` is a `/v3`-level alias of
the CEL-level `ResourceAvailabilityRecord`, not the same shape as the
CEL-level `ResourceAvailability` string union of the same name reachable
through `@originals/sdk/cel`) per historical resource version in the
accepted log, oldest first. `'bitcoin-inline'` means that exact version's
bytes were independently matched inline in an accepted publication;
`'referenced'` means the state names the resource but no accepted
publication in the snapshot carried its bytes on-chain — the expected,
by-design state for any resource beyond the one inlined per publication,
not a defect. This closes #378's remaining scope: the epic's guarantee is
now read as "full signed history is chain-recoverable; resource bytes are
chain-recoverable only when actually inlined, otherwise they remain
authenticated references" rather than the epic's original stronger
"entire asset, no off-chain dependency" wording.

Neither addition changes any previously listed symbol's shape; both are
additive fields/exports.

## Artifact gates

Unchanged from 3.0.0: stable preview packages require consistent local
dependency ranges, a frozen lockfile install, built declarations, consumer
typechecks, Node ESM imports through all exports, browser-safety validation,
local CLI smoke checks, and a packed-tarball consumer test. Include every
referenced JS/declaration/JSON file, the license, and current guide.
Prerelease workspace symlinks alone do not prove the stable artifact. These
API decisions do not establish final review, current regression evidence,
production configuration, or the owner public-host/mainnet proof; those
remain separate release gates — see [#569](https://github.com/onionoriginals/sdk/issues/569).
