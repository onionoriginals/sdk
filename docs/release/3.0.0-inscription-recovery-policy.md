# Landing inscription recovery policy for 3.0.0

This records the existing six-confirmation policy for release gate [#567](https://github.com/onionoriginals/sdk/issues/567).

- `confirmed` records an observed reveal inclusion. It is reversible until retirement. One through five confirmations retain the exact signed commit and reveal, including across a process restart. A provider that reports inclusion without a confirmation count cannot trigger retirement.
- At six or more reported reveal confirmations, the reconciler explicitly retires the pair, removes both transaction payloads, and stops querying that record. A competing superseded pair is retired on a following poll when a retired confirmed winner spends one of its funding inputs. Six confirmations are the application's retention horizon, not a guarantee against deeper reorganizations.
- Before retirement, browser polling checks retained confirmations again. An unconfirmed/missing reveal report demotes the record to `reveal_broadcast` and retries the stored pair. Transport failure during status lookup preserves the last observed state. Broadcast rejection, including missing inputs or conflict, does not restore confirmed status or delete recovery bytes. No replacement pair is constructed, and the Bitcoin node still rejects invalid spends.
- Explicit manual recovery also persists the lost confirmation before attempting a commit retry. A rejected commit returns `commit_broadcast_failed`; the stored status remains demoted and both payloads remain available. An accepted commit followed by rejected reveal remains `commit_broadcast`. Success restores `reveal_broadcast`, subject to later inclusion checks.
- Superseded pairs retain their bytes and remain eligible for reconciliation even if they were previously observed as confirmed. A winning confirmed commit reinstates its original pair and supersedes competing rows. Rival bytes survive until a winner passes the retention horizon.
- `GET /api/btc/inscribe` exposes the observed `status`, never signed transaction bytes. `POST /api/btc/inscribe/rebroadcast` uses those private stored bytes. A retired confirmed record returns confirmed without broadcasting; a retired losing pair returns `not_recoverable`.

The hourly `serve.ts` sweep now invokes the same bounded reconciler used by browser polling. It rotates through at most ten accounts per pass, with the existing five transaction-status reads per account, and refuses overlapping runs. It handles stranded signed pairs and unconfirmed commits by replaying the stored commit before its reveal after the retry interval. It checks retained confirmations and demotes reorged records without needing a browser or synthesizing authentication credentials. It reports unreadable accounts, while the existing stale-record warning and deposit-balance sweep continue. Worklists are rechecked after contested-outpoint reconciliation so a newly superseded rival is never broadcast from a stale list.

This does not close unrelated [#496](https://github.com/onionoriginals/sdk/issues/496) follow-ups, including cross-category lookup starvation and swallowed per-record reconciliation store-write failures.

Verification uses local temporary durable stores, real signed transaction fixtures, public route handlers, and simulated provider responses. Existing tests cover retention, retirement, idempotent retries, and monitoring. The restart test now reconstructs the route instance and store; rejection coverage includes unavailable, missing-input, and conflicting broadcasts. Two new regressions first failed because manual conflict recovery kept `confirmed`, and because a superseded prior confirmation was never reconsidered. Both now pass.

```sh
bun test apps/landing/server/tests/inscribe-routes.test.ts apps/landing/server/tests/inscriptions-store.test.ts apps/landing/server/tests/bitcoin.test.ts
```
