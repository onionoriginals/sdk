## Facts needed for deterministic association

**Bitcoin order.** Core's `getblock` returns the `tx` array by iterating the block's transaction vector, with coinbase at index 0, both for txids and decoded transactions. Therefore a reveal's zero-based transaction position is its position in that array. A block's time, transaction ID lexical order, RPC arrival order and confirmation count are not substitutes. `getblockheader` exposes height/hash and returns `confirmations: -1` for a block outside the active chain. [Core block serialization](https://github.com/bitcoin/bitcoin/blob/9be056a8a72b624dae9623b2f7bded92c2a21c91/src/rpc/blockchain.cpp#L153-L244), [header RPC](https://github.com/bitcoin/bitcoin/blob/9be056a8a72b624dae9623b2f7bded92c2a21c91/src/rpc/blockchain.cpp#L600-L629)

**Inscription ID.** `<reveal-txid>iN` identifies the Nth recognized inscription envelope, starting at zero and flattening inputs in transaction order and envelopes in tapscript order. N is **not an output index**. ord constructs IDs with a counter across inputs and later retrieves the Nth parsed envelope. Pointer fields can direct an inscription to a different output/sat; do not infer assignment from `iN`, input number or assumed `vout: 0`. [ID description](https://github.com/ordinals/ord/blob/7e37a3bd3391044b39f5f11f20dfdb8b3764cd0e/docs/src/inscriptions.md#L111-L133), [parser](https://github.com/ordinals/ord/blob/7e37a3bd3391044b39f5f11f20dfdb8b3764cd0e/src/inscriptions/envelope.rs#L96-L138), [ID/pointer assignment](https://github.com/ordinals/ord/blob/7e37a3bd3391044b39f5f11f20dfdb8b3764cd0e/src/index/updater/inscription_updater.rs#L76-L224), [retrieval](https://github.com/ordinals/ord/blob/7e37a3bd3391044b39f5f11f20dfdb8b3764cd0e/src/index.rs#L1610-L1625)

**Number and list order differ from a universal reveal-order tuple.** Cursed inscription numbers decrease; inscriptions immediately spent to fees are numbered after other inscriptions in the block. Internally ord assigns sequence numbers during location updates, after sorting floating inscriptions by sat offset; its sat enumeration walks the sat-to-sequence table. These are index conventions, not a replacement for explicit block transaction/envelope positions. [Number caveats](https://github.com/ordinals/ord/blob/7e37a3bd3391044b39f5f11f20dfdb8b3764cd0e/docs/src/inscriptions.md#L135-L149), [offset sorting/fees](https://github.com/ordinals/ord/blob/7e37a3bd3391044b39f5f11f20dfdb8b3764cd0e/src/index/updater/inscription_updater.rs#L270-L347), [sequence assignment](https://github.com/ordinals/ord/blob/7e37a3bd3391044b39f5f11f20dfdb8b3764cd0e/src/index/updater/inscription_updater.rs#L428-L449)

**Stable sat versus current location.** Inscription JSON `sat` comes from the inscription entry's assigned ordinal; `height`/`timestamp` come from its creation entry. `satpoint` is the current `txid:vout:offset`. Conversely, `/sat/{sat}`'s `block` and `timestamp` describe when that sat was mined, not when an inscription was revealed. A transfer changes location, not the reveal transaction or assigned sat. Unbound inscriptions can have no assigned sat. [Inscription fields](https://github.com/ordinals/ord/blob/7e37a3bd3391044b39f5f11f20dfdb8b3764cd0e/src/index.rs#L2355-L2386), [sat fields](https://github.com/ordinals/ord/blob/7e37a3bd3391044b39f5f11f20dfdb8b3764cd0e/src/subcommand/server.rs#L727-L791), [assignment](https://github.com/ordinals/ord/blob/7e37a3bd3391044b39f5f11f20dfdb8b3764cd0e/src/index/updater/inscription_updater.rs#L444-L483)

## Enumeration, index health and reorganizations

`/sat/{sat}` JSON contains the full `inscriptions` vector from one enumeration read. Recursive `/r/sat/{sat}` means page 0; `/r/sat/{sat}/{page}` returns **100 IDs per page**, `{ids, more, page}`. Follow consecutive pages until `more: false`; a full page alone proves neither termination nor completeness. The recursive handler returns 404 when no sat index exists, so 404 cannot universally mean an empty sat history. These responses have no snapshot token/block hash. [Enumeration implementation](https://github.com/ordinals/ord/blob/7e37a3bd3391044b39f5f11f20dfdb8b3764cd0e/src/index.rs#L1470-L1529), [recursive pagination](https://github.com/ordinals/ord/blob/7e37a3bd3391044b39f5f11f20dfdb8b3764cd0e/src/subcommand/server/r.rs#L492-L535)

`/status` reports indexed height, chain, sat/inscription/transaction-index capabilities and `unrecoverably_reorged`. `/r/blockhash/{height}` provides the indexed block hash. ord detects parent-hash disagreement, rolls back recoverable reorganizations to a savepoint, and flags unrecoverable ones. Thus a false unrecoverable flag does **not** prove no recent reorganization or no index lag. [Status](https://github.com/ordinals/ord/blob/7e37a3bd3391044b39f5f11f20dfdb8b3764cd0e/src/index.rs#L550-L580), [indexed hashes](https://github.com/ordinals/ord/blob/7e37a3bd3391044b39f5f11f20dfdb8b3764cd0e/src/subcommand/server/r.rs#L3-L29), [reorganization handling](https://github.com/ordinals/ord/blob/7e37a3bd3391044b39f5f11f20dfdb8b3764cd0e/src/index/reorg.rs#L24-L86)

Core `getrawtransaction` without a block hash depends on mempool/txindex availability. With an explicit block hash it can locate the transaction in an available block and report `in_active_chain`. Missing historical data or a pruned block is unavailable evidence, not proof that publication never occurred. [Core RPC contract](https://github.com/bitcoin/bitcoin/blob/9be056a8a72b624dae9623b2f7bded92c2a21c91/src/rpc/rawtransaction.cpp#L217-L248)

## Recommended resolver evidence contract

These are application recommendations, not new Bitcoin/ord consensus rules:

1. **Snapshot:** network, Core tip `{height, hash}`, ord indexed `{height, hash}`, indexer version/capabilities, and enumeration scope/sat. Capture before and after all pages and records; retry/report unavailable if they disagree. Require matching branch hashes and active-chain membership. HTTP bracketing is an optimistic consistency check, not an upstream atomic-snapshot guarantee or cryptographic completeness proof.
2. **Per inscription:** canonical inscription ID, reveal txid, numeric inscription index, assigned sat, creation block `{height, hash}`, and zero-based transaction index verified from that block's `tx` array. Parse the reveal witness with the pinned ord rules to bind the correct envelope and its raw metadata/body; include input index and envelope-within-input index when exposing extraction evidence. Keep current satpoint/address separate and snapshot-qualified.
3. **Explicit ordering:** adopt `(blockHeight, blockTransactionIndex, inscriptionIndex)` as the Originals reveal-order tuple; order multiple CEL entries inside an inscription by their array index. Same-block publications then have a determinate order. Same tuple means the same inscription; conflicting data for it is inconsistent evidence. Never break ties with lexicographic txids, timestamps, inscription numbers or provider list order.
4. **Completeness/result:** report all fetched IDs/pages, terminal-page evidence, inspected range/snapshot and unavailable records. Size caps, timeouts, missing fields, disabled indexes, missing metadata/content or insufficient ordering fields must not become `[]`, a fabricated position or “fully verified.” Fully inspected unrelated/invalid publications can be classified separately by the fold; unread publications cannot be assumed unrelated. Sat-scoped enumeration makes no cross-sat uniqueness claim.
5. **Reorganization recovery:** retain block hashes with cached observations; when their active-chain membership changes, discard/replay affected derived state from a verified surviving prefix. Expose confirmation depth as snapshot-relative evidence; the fold must separately choose any acceptance-depth policy. Unconfirmed records have no confirmed tuple.

No live provider behavior, pagination under concurrent reorganization, raw-envelope extractor, new resolver or authority succession implementation was tested here. The remaining #560 decisions concern when that evidence authorizes transitions; this research does not reverse A's retirement or invent a key-recovery policy.
