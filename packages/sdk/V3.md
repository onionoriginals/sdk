# Originals SDK 4: CEL 3 asset API

This guide describes the SDK 4 identity contract in this checkout. SDK 3.0.0
is already published; the major-version migration is documented in
[Upgrading to SDK 4](../../docs/MIGRATION_4.0.md). The `/v3` entry name and signed
`originals/cel/3` profile remain stable representation names.

The default `@originals/sdk` uses the selected `originals/cel/3`
representation for asset creation, mutation and recovery. `@originals/sdk/v3`
is a smaller local-only entry using the same lifecycle and verifier. The default
SDK also exposes independent DID, credential and low-level Bitcoin utilities.
Both entries read strict SDK 3 envelopes containing CEL 3 history; pre-CEL-3
asset logs and envelopes remain unsupported.

The default SDK provides local custody and mutation, separate WebVH publication,
fresh on-sat asset and DID resolution, and prepared Bitcoin publication with
durable signed-pair recovery. Network evidence is always explicit. A signed
proposal or a broadcast acknowledgement does not establish accepted chain state.

## File provenance and identity

An Original records a controller's signed claims about named files and their
versions. Verification authenticates that history and checks available file
bytes against its signed digests. `asset.id` and `asset.state.assetId` are a
canonical `ni:///sha-256;…` URI derived from the JCS genesis event. Identity stays
constant through edits and publication; `state.alias` starts as that URI and
becomes the current WebVH or Bitcoin alias after migration. A genesis commitment
alone does not establish complete files, current publication or Bitcoin possession.

Originals uses generic CCG CEL with its own application profile. It does not
implement the CCG `did:cel` DID method. `state.didCel` and `deriveDid` remain
explicitly deprecated Originals 3 compatibility aliases. Preserve signed history
and use `normalizeAssetId` / `sameAssetIdentity` from `@originals/sdk/cel` to bind
old records to the canonical identity. See the
[identity contract](../../specs/originals-asset-identity.md).

## Create, edit and load

```ts
import { OriginalsSDK, createLocalSigner } from "@originals/sdk";

// Supply an Ed25519 private key from your own custody; never commit or log it.
const signer = createLocalSigner("Ed25519", secretKeyBytes);
const sdk = OriginalsSDK.create({ signer });
const asset = await sdk.lifecycle.createAsset(
  [{ id: "art", mediaType: "image/png", content: pngBytes }],
  { name: "First edition", metadata: { edition: 1 } },
);

await Promise.all([
  asset.update({ metadata: { edition: 2 } }),
  asset.addResourceVersion("art", revisedPngBytes, "image/png"),
]);

const envelope = asset.serialize();
const fresh = OriginalsSDK.create();
const { asset: restored, verification } = await fresh.lifecycle.loadAsset(
  JSON.stringify(envelope),
);

console.log(verification.verified); // true for complete local history and bytes
console.log(restored.state.resources[0].version); // 2
```

Resource input is `{ id, mediaType, content, url? }`. Content accepts
`Uint8Array`, including subarray views, or a string encoded once as UTF-8.
The SDK copies input bytes before awaiting custody and computes their digest;
callers do not supply a trusted hash. `url` is the profile's ordered URL array.

`asset.state` is immutable state from the core verifier. `asset.resources`
contains authenticated historical versions with available byte copies.
`asset.celLog` and `serialize()` return detached copies. Changing returned
metadata, log entries or buffers cannot alter the instance.

`update({ name?, metadata? })` replaces each supplied field in full; `{ metadata:
{} }` clears metadata. Resource descriptors are replaced through
`addResourceVersion(id, bytes, mediaType)`. Its predecessor and next version
come from authenticated history, never a caller's version number. A new
descriptor does not inherit the old version's hosted URL.

## Custody and mutation results

`CelSigner` names an explicit `algorithm` (`Ed25519`, `P-256`, or `P-384`), a
canonical `did:key` controller, and `sign(message): Promise<Uint8Array>`.
Use the core's `createLocalSigner` or implement that contract in remote custody.
The callback must follow that algorithm's signing semantics and return the
fixed-width signature, not DER. The core authenticates every returned signature.
The older SDK's `OriginalsSigner` is a different interface and is not silently
adapted, particularly for ECDSA hashing.

Pass `{ signer }` on a mutation to override configured custody. A signer supplied
only to `createAsset` is not retained. A signer is unnecessary for loading or
verification. Creation without configured/per-call custody fails `NO_CUSTODY`.
`keyStore` on the default SDK config is only for its independent identity and
credential utilities; it does not implicitly generate or select an asset
controller. `defaultKeyType` likewise configures identity utilities, while an
asset signer explicitly selects its CEL algorithm. Contradictory Bitcoin/WebVH
network settings are rejected before constructing the utility managers.

`rotateKey(newController, { signer })` is signed by the outgoing current
controller. Later operations need the new controller's signer. Retired keys
remain valid for their historical entries. `deactivate(reason?, { signer })`
ends the history: no subsequent operation is permitted. A deactivated history
can still verify; verification does not mean that another mutation is allowed.

Every mutation uses one queue per asset instance across read, sign and commit.
Success returns `{ status: 'signed', head }`. Both the log and resource bytes
commit together. Failures release the queue and leave the previous committed
state intact. Reads during an in-flight edit see the last committed snapshot;
await an edit before serializing if that edit must be included. Separately
loaded instances are independent local histories; this is not a distributed
lock, a merge algorithm, or an idempotency key for external submission.

## Explicitly retained local bytes

Missing custody throws by default. An explicit per-call or configured
`onAppendFailure: 'skip'` returns `{ status: 'skipped', reason: 'NO_SIGNING_KEY' }`.
Invalid input, an unauthorized signer, a custody exception and an invalid
signature always throw, including under this policy.

A skipped resource edit also returns `localResourceId`. Its bytes remain in
`asset.localResources` and `envelope.unverified.localResources`, with no claimed
authenticated version. Name/metadata/rotation/deactivation skips change nothing.
No skipped edit advances the authenticated head or its derived state.

Full verification is false while retained local bytes exist. Default load
rejects that envelope. `loadAsset(envelope, { allowPartial: true })` preserves
it with `verification.verified === false`; history still must authenticate.
This option never bypasses signatures, resource binding, digest checks, or
malformed-input rejection.

`retryResourceVersion(localResourceId, { signer })` signs retained bytes only
while their exact predecessor version and digest remain current. Successful
retry removes that local draft atomically. A stale draft remains available
and requires a deliberate new edit; the SDK never silently rebases it.
`discardLocalResource(localResourceId)` explicitly removes one unsigned draft.

## Interchange and verification scope

Envelope version 4 carries `{ format: 'originals/asset', version: 4, assetId,
eventLog, resources, unverified? }`. `eventLog` is the new `{ log: [...] }`
document. The reader also accepts strict version-3 envelopes with the historical
`assetDid: 'did:cel:…'` field, authenticates their unchanged signed history and
normalizes the returned container to version 4. Version 4 requires canonical
`ni` in `assetId`; mixed-version fields or a mismatched genesis fail. Old signed
migration entries, WebVH method logs and inscriptions are not rewritten.
A resource attachment is exactly `{ id, version, digestMultibase,
content: { encoding: 'base64', data } }`, using canonical padded base64.
Every attachment must match an exact historical resource descriptor and its
actual bytes. Duplicate ids/versions, unproven versions, inconsistent digests
and mismatching bytes fail even during partial load.

`asset.verification()` and `loadAsset(...).verification` use the same checks.
`verified` means all historical resource bytes are present and checked, no local
drafts remain, and the current publication evidence matches the authenticated
head. Local `cel` history needs no network. Hosted histories require a matching
verified WebVH method history and hosted CEL; Bitcoin histories require a fresh
complete accepted sat observation. Missing bytes are listed by id and version.
`allowPartial` retains authenticated history with incomplete publication/byte
coverage. A signed offline Bitcoin continuation remains a local proposal until
accepted by the sat resolver. Verification does not assert Bitcoin finality or
uniqueness across sats. On-sat history alone does not prove the separate WebVH
method binding.

The signed CEL retains its own strict parser and limits. The unsigned SDK
container separately allows up to 32 MiB of retained bytes in total (including
drafts), a 64 MiB JSON envelope, 48 MiB of encoded attachment records (including descriptors),
100,000 attachments in total, and 72 levels of container
nesting. These are SDK memory budgets, not Bitcoin inscription-size promises.
Unknown fields, getters, non-data objects, sparse arrays, duplicate decoded JSON
keys and noncanonical byte encodings are rejected. Metadata values inside the
CEL retain the profile's smaller limits; base64 media does not inherit them.

## Public entry points and removed surfaces

Default and named `OriginalsSDK`, `OriginalsAsset`, `LifecycleManager`, resource
inputs, envelope constants and configuration types describe SDK 4 with CEL 3. The `/types`
subpath matches those root types. The `/cel` subpath exports the selected core:
`parseDocument`, `encodeDocument`, `signEvent`, `verifyEntry`, `verifyHistory`,
and its state and proof types, plus `deriveAssetId`, `normalizeAssetId`,
`assetDigest`, `sameAssetIdentity` and `assetIdFromDigest`. `verifyHistory` returns authenticated controller
history with explicit publication scope, not the old verification-result shape.

Previous `OriginalsCel`, `PeerCelManager`, `WebVHCelManager`, `BtcoCelManager`,
`createEventLog`, `verifyEventLog`, witness factories, `toCelSigner`, and old asset
batch/lifecycle exports are removed from the SDK root. The old asset's
`appendStatement`/holder-write and `rotateBtcoKeys` methods are not on CEL 3 assets.
Use `asset.update` for name/metadata and `asset.rotateKey` for controller changes.
There is no pre-CEL-3 fallback or `@originals/sdk/legacy` subpath.
The previous asset-only `AppendKind`, `AppendCostEstimate`, `InscribeConfirm`,
and lifecycle event payload exports are also removed. CEL 3 operations return
explicit result objects. `EventEmitter` remains an independent typed utility;
the CEL 3 lifecycle does not emit its previous-format asset payloads. Network
preset helpers remain utilities and do not assert a hosted service exists.

Standalone WebVH identity helpers retain their static names on the default SDK,
including `createDIDOriginal`, `updateDIDOriginal`, `prepareDIDDataForSigning`, and
`verifyDIDSignature`; auth uses the same extracted implementation. Those helpers
create/verify identity method documents, not an asset's CEL or publication.
`sdk.did.createDIDWebVH` and `sdk.did.migrateToDIDWebVH` also require an explicit
domain. Missing or blank hosts throw `WEBVH_DOMAIN_REQUIRED`; `webvhNetwork`
only retains utility network mapping and never supplies a hosting domain.
`sdk.did.resolveDID` derives Bitcoin controller documents from the same fresh
accepted history as asset resolution and throws `ASSET_RESOLUTION_INCOMPLETE`
when evidence is unavailable, even if an older document is cached. `did:cel`
identity resolution remains unsupported. WebVH identity resolution by itself
is not verification of an Original.

## Local command line

The installed `originals-cel` command uses CEL 3. Supply an explicit algorithm
and a raw binary private-key file (32 bytes for Ed25519/P-256, 48 for P-384):

```sh
originals-cel create --file art.png --media-type image/png --algorithm Ed25519 --key controller.key --output asset.json
originals-cel verify --asset asset.json
originals-cel inspect --asset asset.json
originals-cel verify --log history.cel.json
originals-cel verify --log history.cbor --format cbor
```

Creation emits a complete version-4 envelope and refuses to overwrite an existing
output file. `verify --asset` requires full local history and all byte attachments.
`inspect --asset` can describe an explicitly partial envelope; signatures and
supplied bytes still validate. `verify --log` authenticates controller history
only and prints `verified: false` with that scope because resource/publication
evidence was not checked. A successful history check exits zero; a failed check
exits nonzero. The CLI provides no migrate, publish, inscribe, or network resolver
command during this integration stage. Run `--help` for its current interface.

### Bitcoin snapshot resolution

Configure `satProvider: { getSatSnapshot(sat) }` on the default SDK, or use an
`ordinalsProvider` implementing that optional method. `RegtestProvider` obtains
raw inscription metadata and creation-block ordering from local ord and Core.
Each call reads fresh evidence; earlier-format provider methods alone do not
establish the complete observation needed by CEL 3.

`lifecycle.resolveAssetFromSat(sat)` returns a status union. An `accepted` result
contains the asset, independently checked resource-byte coverage, and the core's
provider-qualified sat resolution. Missing historical bytes remain explicit.
`did.resolveDIDWithMetadata(did)` exposes the same head, deactivation and live
ownership separately from the derived controller document. Ordinary DID reads
fail on incomplete evidence and return no active document for deactivation.
Network asset `verify()` and `loadAsset()` re-read the snapshot; serialized
publication claims never replace that check. Cross-sat canonicality and the
separate WebVH method binding remain explicitly unverified.

Every `SatResolution` (accepted or not) also carries `chainEvidence:
'provider-asserted' | 'node-validated'`, copied from the optional
`SatSnapshot.chainEvidence` the provider supplied (omitted defaults to
`'provider-asserted'`). No shipped provider (`RegtestProvider`,
`QuickNodeProvider`) performs independent chain validation today, so every
current resolution is `'provider-asserted'`: chain tip, block, and reveal-
position facts are trusted assertions from the same service that supplies
Ordinals interpretation, not confirmed by a separately validating Bitcoin
node. `resolveSat` never upgrades this qualifier on its own; it only reflects
what the snapshot claims. `did.resolveDIDWithMetadata(did)` surfaces the same
field on `didDocumentMetadata.chainEvidence`. Treat `verification.verified`
and an `accepted` status as authenticated CEL history and content, not as
independent proof of Bitcoin consensus.

### Hosted publication

`lifecycle.publishToWeb(asset, { domain })` publishes the CEL 3 document and
historical resource bytes beside a separate, independently verified WebVH method
log. It returns `{ status: 'published', did, asset }`; keep the returned asset.
The input remains a local snapshot, so concurrent local edits do not disappear.
The host is required. Default paths are
`published/anonymous/<genesis-digest>/`; resource paths use the signed digest.
Method-log custody must be Ed25519; pass `webvhSigner` separately when the asset
controller uses P-256 or P-384.

For explicit retry control, call `prepareWebPublication` then
`publishPreparedToWeb`. Preparation signs without uploading. A partial upload
error retains the prepared publication in its details; retry that object to keep
the same identity and signed history. CEL is uploaded last. Calling
`publishToWeb` again with an edited hosted asset retains its permanent alias and
publishes all historical resource versions. Storage is responsible for access
control and durable persistence; this is not a distributed publication lock.

A fresh configured SDK calls `resolveAssetFromWeb(did)` to validate both signed
histories and recover the bytes. It refuses missing or substituted resources.
`verify()` re-reads the hosted evidence, and `loadAsset` uses that same path.

### Bitcoin publication and recovery

`prepareBitcoinPublication(asset, { fundingUtxos, satSigner, changeAddress,
feeRate, signer?, inlineResourceId? })` builds and signs without broadcasting.
A boundary starts from the exact verified hosted head, appends the controller's
`webvh → btco` migration, and carries the complete CEL. A later Bitcoin
publication contains only signed entries after the freshly accepted sat head;
divergent, stale and empty continuations are rejected.

The default boundary inlines its first current resource, and a delta inlines its
first changed current resource. `inlineResourceId` selects another current
resource; `null` makes a log-only `application/cel` JSON inscription. Inline
media uses raw bytes as the inscription body and CEL CBOR as metadata. At most
one current resource is inlined per publication; other descriptors remain
references. Missing historical bytes remain visible to the reader.

The first funding input must start with the identity sat; the builder checks its
sat ranges, and updates additionally require the accepted inscription's current
satpoint. Nonzero offsets require prior alignment outside this API. The complete
serialized envelope is included in fee sizing and is limited to a supported
390,000-byte inscription script before Bitcoin signing.

Persist the full JSON-serializable `PreparedBitcoinPublication` to retain the
asset proposal and both signed transactions across process termination. Submit
with `publishPreparedToBitcoin(prepared, { recoveryStore })`. Direct broadcasting
requires an `InscriptionRecoveryStore` whose save operation is atomic and durable;
a provider's `submitInscription` may instead own that persistence. No implicit
memory store is provided. `publishToBitcoin` is the prepare-and-submit convenience.

The result is `{ status: 'submitted' | 'broadcast-unknown', asset, submission }`.
Keep the returned proposal, and use fresh `resolveAssetFromSat` to establish
acceptance and byte coverage. An ambiguous result retains locally computed
transaction ids and exact signed bytes. Retry the same prepared wrapper; never
rebuild merely because an acknowledgement was lost. Low-level
`prepareInscriptionOnSat`, `submitPreparedInscriptionOnSat` and
`resumeInscriptionOnSat` expose the same pair-persistence contract. Recovery
rechecks current confirmation; a saved prior acknowledgement is not terminal.
Before persistence or broadcast, submission verifies the reveal's single-leaf
Taproot commitment and Schnorr signature against the actual commit output.
Transaction ids alone do not authenticate witness bytes. HTTP integrations can
call the root `validateInscriptionReveal(commit, reveal)` utility with parsed
`@scure/btc-signer` transactions; it accepts the writer's one-inscription script
path with default signature hash and throws for unsupported or invalid witnesses.

`QuickNodeProvider.getSatSnapshot` accepts a `contentBaseUrl` for an ord-compatible
raw `GET /content/:id` endpoint, preserving arbitrary PNG bytes without string
decoding. Otherwise it requires explicit `contentEncoding` matching the gateway
contract. The documented UTF-8 response covers text; `base64` requires a gateway
verified to encode bytes that way. A live binary deployment must verify its chosen
endpoint against known inscription bytes. `auto` never
attests CEL 3 snapshot bytes. Raw CBOR metadata, complete enumeration, index health
and active block order are required. Provider-detected chain movement triggers
bounded fresh retries; persistent incomplete evidence fails closed.
QuickNode and regtest providers also enforce a total budget per observation:
30 seconds and 512 upstream requests by default, with cancellation propagated to
HTTP reads. Their `snapshotBudget: { timeoutMs, maxRequests }` option can adjust
these limits (at most 120 seconds and 50,000 requests). Exhaustion raises
`SAT_SNAPSHOT_BUDGET_EXCEEDED`, stops further reads, and never returns a partial
snapshot as complete evidence.

For synchronous browser recovery lists, import `parseAssetEnvelope` from
`@originals/sdk/asset-envelope`. This offline entry authenticates the same strict
v3/v4 envelopes without loading hosting, Bitcoin or custody modules.
Use `inspectAssetEnvelope(input)` when the caller also needs the derived state:
it returns `{ envelope, history }` from one authentication pass. `history` is the
core verifier's immutable controller-history result; it does not establish
resource-byte coverage, hosted publication or Bitcoin acceptance. The returned
envelope is a detached mutable copy. Editing it does not change the history
result, and later SDK ingestion authenticates the edited input again.
