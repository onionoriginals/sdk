# Originals CEL 3 core (CEL package 2)

The CEL 3 implementation is exported as `@originals/cel/v3` (also `celV3`
from the package root). It implements the selected context-free CCG application
profile. SDK 4 / CEL 2 retain that signed representation with canonical `ni`
asset identifiers. SDK 3.0 is already published; this is a major-version identity
change, documented in [the migration guide](../../docs/MIGRATION_4.0.md).
The core supports asset creation, mutation, publication and recovery; see [the SDK API guide](../sdk/V3.md) for those integrations. The
standalone CEL package root retains earlier APIs. Pre-CEL-3 histories remain unsupported by this core. SDK 3 envelopes containing
CEL 3 history have a strict authenticated read path; signed events stay unchanged.

CEL 3 proofs use `DataIntegrityProof` with `eddsa-jcs-2022` (Ed25519) or
`ecdsa-jcs-2019` (P-256/P-384). The custom `originals-cel-ed25519-jcs-v1` label
belongs to retained previous-format code and is rejected here. The
`originals/cel/3` application-profile identifier is separate from the cryptosuite.

The contracts are [wire/proofs](../../specs/originals-cel-v3-profile.md) and
[authority/order](../../specs/originals-cel-v3-authority.md). The [identity contract](../../specs/originals-asset-identity.md) supersedes their
historical asset spelling. Independent reference manifests retain their signed
values; this document describes the current implementation. This is an application profile of a community draft,
not certification of every CCG feature or application.

## Public boundaries

| API | What it establishes |
| --- | --- |
| `decodeValue` / `encodeValue` / `canonicalizeValue` | Bounded, noncoercing JSON values; strict JSON or the JSON subset of CBOR; RFC 8785 / RFC 8949 output. No authority. |
| `parseDocument` / `validateDocument` / `encodeDocument` | All retained CEL 3 fields and canonical encodings. Unknown fields and old wrappers fail. Proof objects are accepted; writers emit arrays. No authority. |
| `eventDigest` / `deriveAssetId` / `digestBytes` | Event multihash, canonical `ni` identity from genesis, or a digest of exact resource bytes. Proofs never select event identity. |
| `verifyEntry` | Every supplied proof authenticates a did:key signer. A valid signer may still be unauthorized for this event. |
| `verifyHistory` | Every signature, preceding link and authorized operation passes; one immutable derived state. An input prefix must be an actual result from this verifier instance. An optional portable `checkpoint` is independently confirmed against the presented history and reported as separate `freshness`, never trusted on its own. |
| `checkpointFromHistory` | A portable, serializable `{ assetId, head, entryCount }` claim extracted from a `VerifiedHistory`, for a caller to persist or hand to a different verifier/process. |
| `resolveSat` | The same history fold plus complete, consistent provider observations and whole-publication ordering at one identified snapshot. |
| `createLocalSigner` / `signEvent` / `createNonce` | Explicit Ed25519, P-256 or P-384 signing. A returned signature is locally checked; the history/append caller must still check authority before publishing. |
| `parseAssetDid` | Retained parser name; canonical bare `ni`, historical Originals 3 `did:cel`, or publication alias syntax. `ni` retains the `method: 'cel'` discriminator for compatibility; it is not a DID-method claim. WebVH SCID encoding is checked; its separate method-log binding remains unverified. |

`CelError` carries `status` (`invalid`, `unsupported`, `history-required`, `limit`)
and a specific `code`. A well-formed signed delta without its prefix returns
`history-required`; invalid internal links/signatures fail first. Multiple proofs
must all validate and identify the current controller. ECDSA accepts high-S
signatures and hashes the concatenated document/configuration hashes as a
message. `jcsSigningMessage` and `verifyJcsSignature` are cryptographic primitives
for interoperability/known answers; they do not establish application policy.

## Asset identity

`state.assetId` and its initial `state.alias` are a canonical RFC 6920
`ni:///sha-256;…` URI committing to the full validated genesis event's JCS bytes.
The URI contains the raw 32-byte hash; event links still use the existing
SHA-256 multihash. The resource digest still commits to exact file bytes.
Neither identity spelling proves controller authority or available file bytes.

`deriveAssetId` derives canonical identity from genesis; `assetIdFromDigest`
converts an existing event multihash. `assetDigest`, `normalizeAssetId` and
`sameAssetIdentity` support strict comparison with historical Originals 3
`did:cel` aliases. Deprecated `deriveDid` and `state.didCel` expose the old
Originals spelling only; no CCG DID-method implementation is provided.

`verifyHistory` and `resolveSat` accept `expectedAssetId`. Deprecated `expectedDid`
remains readable; when both are supplied, both must bind the same genesis.
Signed historical migration sources and WebVH bindings retain their original
values. Normalization never edits a proof or changes an inscription.

## Offline creation and continuation

```ts
import {
  createLocalSigner, createNonce, digestBytes, signEvent,
  verifyHistory, encodeDocument,
} from '@originals/cel/v3';

// secretBytes comes from the application's explicit key-management choice.
const signer = createLocalSigner('P-256', secretBytes);
const creation = await signEvent({
  operation: {
    type: 'create',
    data: {
      profile: 'originals/cel/3',
      controller: signer.controller,
      createdAt: new Date().toISOString(),
      nonce: createNonce(),
      name: 'My Original',
      resources: [{
        id: 'art.png', mediaType: 'image/png',
        digestMultibase: digestBytes(pngBytes),
      }],
    },
  },
}, signer);
const first = verifyHistory({ log: [creation] });
const change = await signEvent({
  previousEvent: first.state.head,
  operation: {
    type: 'update',
    data: { profile: 'originals/cel/3', name: 'New title' },
  },
}, signer);
const next = verifyHistory({ log: [change] }, { prefix: first });
const jsonBytes = encodeDocument({ log: [creation, change] }, 'json');
```

The verifier copies input and freezes its result. A serialized/copied state is
not an authenticated prefix: reverify the saved log after restart. This instance
provenance guard is not a Bitcoin boundary cache. The shared state contains the
current controller, controller intervals, active status, head, aliases, resource
versions and metadata. It contains no holder authority and no fabricated update
time derived from a proof timestamp. Metadata updates replace the whole object.

## Freshness and portable checkpoints

`verifyHistory`'s `prefix` mechanism (above) authenticates continuation within one
verifier instance; it is not a claim about whether the presented history is the
latest or only branch, and a `prefix` object cannot be serialized, persisted, or
handed to a different verifier or process. `result.freshness` is `"unknown"` in
the ordinary case (no checkpoint supplied): a first-time verifier simply has no
basis to claim it is looking at current state, only that the presented state is
authentic.

A recipient that wants to detect rollback or a diverging continuation across
process boundaries — for example, a private (non-Bitcoin-anchored) CEL that a
holder re-presents after time has passed — persists a portable checkpoint
instead:

```ts
const first = verifyHistory({ log: [creation] });
const checkpoint = checkpointFromHistory(first); // { assetId, head, entryCount }
// ...persisted by the application, e.g. to disk or a database row...

// Later, in this process or a different one, with no shared prefix object:
const later = verifyHistory(currentLog, { checkpoint });
// later.freshness === "checkpoint-consistent" only if `currentLog` authenticates
// to the same asset and either equals or strictly extends the checkpointed head;
// an inconsistent or shorter (rolled-back) history throws instead.
```

`checkpoint` and `prefix` compose: a checkpoint can name any entry count already
covered by the call, whether reached through `prefix` chaining or from full
history in `document.log`. Verification never trusts the checkpoint's own claim —
the recorded head at the checkpoint's `entryCount` must actually match what this
call authenticated, or verification fails closed (`CEL_CHECKPOINT_ASSET`,
`CEL_CHECKPOINT_ROLLBACK`, `CEL_CHECKPOINT_FORK`). Persisting a checkpoint, and
deciding when its absence should block an operation, is an application/recipient
policy choice; `verifyHistory` never persists one on its own. `"externally-anchored"`
is a reserved `freshness` value for future witness/Bitcoin-anchoring evidence and
is not produced by this function today.

An external `CelSigner.sign(message)` must sign message bytes as Pure Ed25519 or
ECDSA using the selected curve's message hash, returning fixed-width signature
bytes. For a prehashed HSM API, hash the provided message exactly once with
SHA-256 / SHA-384 respectively. Do not sign it as a Bitcoin sighash, DER signature,
Ed25519ph, or silently switch the configured algorithm. Reject remote-signer
failures before invoking publication. `signEvent` authenticates the proof, while
`verifyHistory` enforces which controller is allowed to sign the event.

## Bitcoin evidence boundary

`resolveSat(snapshot, { expectedAssetId? })` does not fetch or broadcast. The adapter
must collect all pages, complete content and metadata (explicit null for absent),
creation block/hash/tx position, the numeric inscription suffix, active-chain
block transaction lists, healthy synchronized index tips before/after the read,
and separate current ownership. `blocks` are adapter assertions of active-chain
membership; the core neither verifies Bitcoin consensus nor proves an indexer's
completeness. Index trust is explicit.

The first valid complete boundary fixes identity independently of the requested identity.
Each subsequent publication must extend the accepted head and be in a strictly
later block. That height gate applies once per publication. A batch that rotates
to B and then appends with B is valid; a bad second entry rejects the whole batch.
An invalid inspected candidate is skipped with a diagnostic; missing data,
conflicting observations or unavailable required capabilities prevent an accepted
result. Re-run from fresh observations after a reorg; there is no stale-head
fallback. `pending` inscriptions cannot advance history.

An accepted result means **accepted at the supplied sat snapshot**. It exposes
`scope: 'sat'`, `crossSatCanonicality: 'unknown'`, the chain tip, derived publication
evidence, and ownership separately. It does not prove finality, global uniqueness,
all remote resource bytes, or WebVH method binding. `inlineResourceIds` lists only
resources whose current signed media type and byte digest match the inline
content. Unmatched inline bytes receive an explicit status/diagnostic; they do
not discard otherwise authorized history or change fork selection. A resource file is still raw bytes, with the CEL in CBOR metadata;
without metadata, CEL is read from `application/cel` JSON content.

Offline btco history is `scope: 'controller-history'` with
`bitcoinAcceptance: 'unverified'`, including otherwise valid signed continuations.
It is not a writer's current on-sat head. Writer integration must resolve the sat
freshly, serialize competing local writes, verify the exact delta and report a
paid losing fork explicitly. Normal DID resolution and SDK operations must consume
this shared state rather than repeat authority logic.

## Deliberate limits and remaining integration

- `dataReference` and `previousLog` are recognized CCG features outside this
  inline Originals profile. They return `unsupported`; there is no retrieval
  callback or dropped reference. Old custom proof labels, holder fields and
  wrappers do not verify on this path.
- WebVH's ASCII DNS/path/SCID syntax is checked. IDNA2008 domain validation is
  not implemented; Unicode/`xn--` domains return `CEL_WEBVH_IDNA`, and an otherwise
  required publication yields `unsupported-capability`. They are not mislabeled
  an invalid signature. Separate WebVH log/SCID/controller binding is still
  required in the SDK/hosting/resolver stage. See the [method specification](https://identity.foundation/didwebvh/v1.0/#method-specific-identifier).
- The profile's 10 MB transport/canonical limit, depth/value/string limits and
  per-document/resource/proof bounds are enforced. Large valid logs can require
  substantial signature-verification time; use an isolated worker where blocking
  browser UI is unacceptable. The existing regtest provider's 5 MiB response cap
  must be reconciled before new-format Bitcoin writes.
- The package root retains old APIs for previous-format integrations. SDK 4
  uses this CEL 3 core with the updated identity contract. Core tests alone do not establish hosted or Bitcoin
  integration; see the [release verification report](../../docs/release/2026-09-07-open-pr-review.md)
  for the separate SDK and real-regtest evidence.

Run `bun test tests/v3/` from `packages/cel`. The tests consume saved independent
reference outputs, literal RFC/W3C vectors, and independent Node/OpenSSL proof
checks. The [companion authority cases](../../docs/research/cel-core-vectors/README.md)
use declared Bitcoin observations; they are not fabricated regtest evidence.
